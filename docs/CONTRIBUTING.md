# Contributing

English · **[Español](es/CONTRIBUTING.md)**

## Workflow

1. Start from the latest `main` and create a branch named for the work:
   `feature/...`, `fix/...`, `content/...`, `design/...` or `docs/...`.
2. Make the change. Keep one topic per branch and small, clear commits in English.
3. Run the checks in [DEVELOPMENT.md](DEVELOPMENT.md#checks-before-a-pull-request).
4. Open a pull request to `main` with a short description and a «How to test»
   list. GitHub Actions must pass.
5. Merging to `main` publishes the change to the live site, so merge only what is
   ready.

## Rules

- **Keep the docs current.** When your change adds, finishes or changes a
  feature, update its row in [FEATURES.md](FEATURES.md) (status, and how it works
  today) and any doc whose facts changed: routes, endpoints, scripts, roles,
  models. Do it in the same pull request, in English and in Spanish
  (`docs/es/`), and mention it in the pull request description.
- **Spanish for visitors.** Everything shown on the site is in Spanish (Mexico).
  Code, comments and commit messages can be in English or Spanish.
- **Follow the design guide.** [DESIGN.md](DESIGN.md): use the tokens and
  classes in `src/index.css` (`.tp-card`, `.tp-button`, ...). No new colors,
  fonts or shadow styles.
- **Accessibility.** Real `<button>`, `<a>` and `<label>` elements, 4.5:1 text
  contrast, and every page works at 375 px wide.
- **Commits.** Use your own Git identity. Commits have human authors only: no
  co-author or "generated by" trailers.
- **Data.** Never commit secrets or `.env`. Change live data only through the
  guarded scripts, and try them on `teacherperi` before `teacherperi_prod`.
- **Content.** Never copy a problem into a list, exam or lesson; reference it.
  Don't publish empty lessons; show «Próximamente» instead. Don't add math
  content (problems, lessons, solutions) without review: official content goes
  through [CONTENT.md](CONTENT.md).
